# Архитектура 2D-игр

## Общая модель

Каждая игра в каталоге `2d` — автономный HTML-документ. Разметка, стили, состояние и игровой код находятся в одном файле; сборщик, фреймворк и серверное API не нужны. Страница получает ввод через DOM Events, изменяет модель игры и обновляет представление.

Большинство игр рисуются через Canvas 2D и следуют циклу `input → update → draw → requestAnimationFrame`. Исключения — Minesweeper и Tic-Tac-Toe: их поле состоит из DOM-элементов и перерисовывается после хода. Состояние хранится в обычных объектах и массивах JavaScript и при перезагрузке страницы сбрасывается.

## Потоки выполнения

Непрерывные игры запускают `requestAnimationFrame`; часть логики использует счётчик кадров, часть — время кадра. События клавиатуры, указателя, касания и датчиков только меняют управляющее состояние или создают игровые сущности. Затем update-функция применяет движение и коллизии, а draw-функция заново рисует кадр.

DOM-игры работают событийно: обработчик хода меняет массив клеток, проверяет завершение и вызывает `render`. Это делает Minesweeper и Tic-Tac-Toe удобными для тестирования по видимым элементам.

## Ограничения и расширение

- Код не разделён на модули, поэтому общие функции ввода, аудио и хранения результатов пока дублируются.
- Результаты не сохраняются между сессиями; для рекордов можно добавить `localStorage`.
- Canvas-играм полезно постепенно отделить чистую игровую модель от отрисовки: это упростит unit-тесты физики и коллизий.
- Сенсорные API требуют разрешения пользователя и HTTPS на реальном устройстве; игры предусматривают клавиатурный fallback там, где это возможно.
